Which parts of a tool's documentation does a model actually need?

Four models ran the same 200 multi-turn tasks under six documentation conditions. This report follows the trajectory analysis plan: headline sensitivity, paired statistics, where in the tool-use process documentation matters, behaviour under missing documentation, failure analysis, cost, and four systematically chosen case studies cited to their trajectory files.

Summary

1. Documentation sensitivity

The conditions remove one documentation component at a time. D0 is the original BFCL schema. D1 removes tool descriptions, D2 removes parameter descriptions, D3 replaces tool names with tool_NN, D4 replaces parameter names with arg_N, and D5 applies all four. Types, required lists, enums and defaults are kept everywhere. Success is BFCL's own multi-turn evaluator: the backend state after every turn must match the ground-truth state and the required call outputs must be present.

2. Paired task-level statistics

Each ablation is compared with D0 on the same 200 tasks. The two discordant cells (tasks that pass only in D0, tasks that pass only in the ablation) carry the evidence; the exact McNemar test and a task-level paired bootstrap confidence interval are computed from them. With 20 comparisons, treat p below 0.0025 (Bonferroni) as the conservative threshold; everything else is exploratory.

3. Where documentation matters: selecting tools vs constructing arguments

The plan asks whether documentation helps the model pick the right tool or fill in the right arguments. Both are measured against the ground-truth call list. For each ground-truth call in turn t, a tool hit means the model called that tool by the end of turn t; an exact hit means it did so with identical arguments. Tool-selection accuracy is tool hits over all ground-truth calls; argument accuracy is exact hits over tool hits, so it is conditional on having chosen the right tool.

4. Which descriptions matter

For every ground-truth call where the model used the right tool but wrong arguments, the closest same-tool call was found and the parameters whose values differed were recorded. Counting those parameters in D2 and subtracting the D0 count isolates the argument errors that appear when parameter descriptions are removed. The table quotes the description that was removed.

5. Tool-use behaviour

Does a model compensate for missing documentation by interacting more? Calls are counted from BFCL's decoded tool calls; a step is one model request (a plain-text reply also counts as a step and ends the turn). Calls are classed as on-path when the tool appears anywhere in the task's ground truth, off-path when it does not but executed without error, and failed when the backend returned an execution error.

10. Method, definitions, caveats

Harness. BFCL's own multi-turn loop, backend classes and evaluator were used unchanged (commit in the header). The study code subclasses BFCL's OpenAI-compatible handler to route requests to OpenRouter, swap in the ablated schemas, and translate the model's calls back to original names before execution. Temperature 0.001, BFCL's default. Model, provider, timestamps, retries and full raw request and response bodies are stored per trajectory.

Definitions. A call is a tool call BFCL decoded from the model's response; malformed calls that BFCL could not decode end the turn and are not counted. Repeated call: identical tool and arguments to an earlier call in the same task. Exact hit requires equality of every argument value after string normalisation; a semantically equivalent but differently spelled value counts as a miss, which makes argument accuracy conservative in every condition equally. First divergence: the first ground-truth call, in turn order, with no exact hit.

What the results support. On this benchmark, parameter descriptions are the documentation component the models depend on, and the dependence is at the argument-construction step rather than tool selection. Removing all four components removes the ability to do the tasks at all, for every model.

What they do not support. That tool descriptions or names are unnecessary in general: the tools here have descriptive names, the user prompts name the actions, and tool outputs remain fully informative. That models cannot learn a tool interface through interaction: BFCL caps a turn at 20 steps and scores the final state, which penalises exploration. That the D2 effect is purely semantic: the descriptions that matter most encode value formats and allowed values that the schema does not carry structurally, so part of the effect is missing structure rather than missing meaning. Latency is not compared because provider routing differs per model.

Data. All numbers are recomputable from runs/main2/analysis.json (metrics) and runs/main2/index.json (one row per trajectory). Each trajectory file holds the task, the exact tools sent, name maps, BFCL's result and log with backend state after each turn, every raw API exchange, token and cost totals, and the evaluator verdict.
